# PMS AI chat quality and feedback remediation

The chat should answer the requested question in the first sentence, using verified PMS data for the requested period and scope. An Admin should be able to diagnose a bad answer, verify a correction, and measure whether the next answer improves.

## Phase 1 · Correct the chat answer and its presentation

- Preserve explicit country, month, level and question intent through validation, tool execution and rendering. Treat a scoped request for overall performance as a valid review. Ask one short clarifying question when a missing choice would materially change the answer. Report missing or unpublished data for the requested period without silently substituting the latest month.
- Use the authorized PMS department, team and metric catalog for scope resolution across Egypt and UAE. Keep Call Center scenarios for Call Center selections. Start other scopes with a direct performance review and offer KPI or trend prompts appropriate to the selected scope. Test transitions from Call Center to other departments and back, including an explicit change in country or level.
- Validate that the result has the metric, subject and period the user asked for before drafting. Use the existing PMS sources and authorization checks. Fix any reproduced mismatch at its owning stage and use the same answer contract for model and fallback responses.
- Make the first visible sentence the answer. Brief mode may show up to two supporting points when they add distinct, verified facts. Put evidence, charts and detailed breakdowns behind **View details** when the question does not require them upfront. Offer one relevant follow-up when it helps. A clarification should show only the question and any actionable choices.
- Keep the UI duplicate check as a final safeguard. Remove repeated claims upstream using their subject, metric and period when those fields are available. Preserve a supporting point if it adds a distinct fact. Use the same concise answer when copying or reopening a conversation.

**Exit criterion.** The exact prompt and paraphrases resolve to UAE and September, with the response matching the PMS source. Test an equivalent Egypt request, a period correction, a country correction, a missing month, restricted access, a genuine clarification and provider failure. Verify once-only rendering in Brief mode, with evidence available on demand. A correct headline paired with a repeated paraphrase fails the presentation check.

## Phase 2 · Make feedback diagnosis observable and reliable

- Make the intended flow easy to complete in Admin at desktop and mobile widths. Open **Inspect**, run **Analyze Root Cause** or **Summarize Cluster**, and show the result next to the selected trace. Show distinct outcomes for incomplete output, privacy quarantine, quota, authorization, misconfiguration and provider error. Summarize the finding first and place raw trace details behind expansion.
- Return a useful diagnosis only after validating the category, nonempty summary and supporting field types. Record model and prompt versions alongside the result. Make cache reuse conditional on trace revision and analyzer configuration. Label cached results and keep **Re-analyze** available after provider or configuration changes. A failed attempt should leave the last valid diagnosis accessible with its original provenance.
- Keep the current Admin authorization and redaction checks in the full request path. Use synthetic traces for live smoke tests. Report usage separately from readiness. Surface a provider failure as a provider failure even when quota remains available.

**Exit criterion.** One signed-in trace diagnosis and one cluster summary succeed with the configured provider in staging. Verify mock coverage for empty and malformed output, timeout, 429, disabled or missing credentials, stale cached output and privacy quarantine. Confirm denied roles and quarantined inputs produce zero outbound calls. The diagnosis of the selected trace remains associated with that trace when the reviewer changes selection during a request.

## Phase 3 · Close the feedback-to-improvement loop

1. For each reviewed failure, capture a concise explanation, the intended behavior, an expected PMS fact or reference when applicable, and the component that owns the correction. Route wording, data parity, and access defects to their respective code or data owners. Use approved patterns for verified routing corrections.
2. Preview a proposed routing change against the exact prompt, varied wording, and similar prompts with different intent. Show before and after operation, scope and period next to the PMS check. Allow a verified Admin to approve or reject. Store no static employee answers in patterns. An approved hint can influence interpretation only inside the authorized request and evidence pipeline.
3. Verify the active chat path consumes the correction. If the matcher is reachable only on some routes, explicitly choose where hints should participate, add an integration test for that path, and preserve field precedence and access checks. Record whether the hint matched, was overridden, or was skipped. Recompute the response from current PMS evidence.
4. Track reviewed feedback by outcome. Use **Needs diagnosis**, **Needs verification**, **Correction applied**, or **Engineering fix required** where they correspond to an actionable state. Mark a case resolved after replay verifies the improvement. Keep negative feedback available for review and controlled evaluation.

**Exit criterion.** Demonstrate one routing failure end to end. A flagged reply gets a diagnosis, an Admin verifies and approves the pattern, and a fresh chat on the active path answers the original and paraphrased request correctly without changing unrelated requests. Demonstrate one formatting failure closed by the response contract. Deactivating the pattern removes its effect on a fresh request.
